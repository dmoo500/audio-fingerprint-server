# MusicBrainz and pending metadata

## Optional metadata enrichment

Availability checks never contact MusicBrainz: they use only already published references with a verified recording key. ISRC queries use the stored identity plus title, artist and duration matching; an ISRC-only reference without a verified MBID cannot be considered full. A check does not alter references, recordings, or statistics.

Set `FP_MUSICBRAINZ_ENABLED=true` and `FP_MUSICBRAINZ_CONTACT` to a suitable contact. `FP_MUSICBRAINZ_BASE_URL` defaults to `https://musicbrainz.org/ws/2`; set it to another MusicBrainz-compatible API base for a self-hosted instance, including any path prefix:

```sh
export FP_MUSICBRAINZ_ENABLED=true
export FP_MUSICBRAINZ_CONTACT="operator@example.org"
export FP_MUSICBRAINZ_BASE_URL="https://metadata.example.org/musicbrainz/ws/2"
```

The worker uses `/recording/{mbid}?inc=artists+isrcs+releases&fmt=json` and `/isrc/{isrc}?inc=artists+releases&fmt=json`. HTTP is supported for explicitly configured local instances; use HTTPS for remote endpoints. Embedded credentials, query strings and fragments in the base URL are rejected. Both Compose modes pass these settings through; recreate the service after changing them. Inside a container, `localhost` refers to that container, so use a hostname reachable from the backend. Cache keys include the API endpoint and response version, so older cache entries and results from a different endpoint are not reused.

The worker validates supplied recording MBIDs and ISRCs, checking their relationship when both are supplied; it does not look up recordings by song title alone. Redirects are withheld rather than assumed valid. Lookups are paced at least 1.1 seconds apart and cached for seven days, including empty and ambiguous results; outages are not cached. HTTP 429, 502 and 503 pause the whole worker and defer the current submission without consuming an attempt. HTTP 503 starts with a 60-second pause; each consecutive HTTP 503 adds ten seconds, up to 15 minutes. An actual HTTP 200 or 404 resets the backoff, so the next HTTP 503 starts at 60 seconds again; cache hits do not reset it. HTTP 429/502 retain exponential backoff starting at 30 seconds, up to 15 minutes. A longer `Retry-After` delay always takes precedence. Other HTTP and network failures retain the three-attempt retry limit for initial processing; pending rechecks instead defer without consuming a completed check. Only missing metadata is filled, and an album is filled only when the returned release list is complete and has one distinct title. Unresolved results follow the bounded pending lifecycle below. MusicBrainz validates identifiers and metadata, not that submitted fingerprints match the recording or that the audio is authentic.

MusicBrainz HTTP handling, identifier verification, cache access and service-wide pacing/backoff live in `fingerprint_server/musicbrainz.py`; the worker owns submission orchestration and publication. A supplied recording MBID can disambiguate several ISRC recordings, but must agree with the ISRC in both lookup directions. For a complete list with multiple recordings, the first candidate matching the supplied title, an artist credit or available alias, and any available duration within eight seconds is selected. Name comparison approximates MA's loose comparison without depending on MA's helpers; this metadata heuristic does not verify the audio. If no candidate matches, the confirmed ISRC still permits publication when supplied metadata is complete, without assigning a recording MBID or grouping by ISRC. Missing metadata still leaves the submission pending, and incomplete lookup lists do not confirm the ISRC. Per the [MusicBrainz lookup contract](https://musicbrainz.org/doc/MusicBrainz_API#Lookups_for_other_unique_identifiers), ISRC lookup lists are unpaged and complete even without `recording-count`; a single result is not marked ambiguous just because that optional count is absent. Cache parser version 3 excludes older results without requeueing existing pending submissions or changing reference verification versions.

The shared cooldown is held in memory and resets on restart, but the current submission's delayed retry remains in the queue. Even submissions that could use cached results wait for the cooldown before being claimed. Logs distinguish service-wide cooldowns from per-submission failures, show retry delays in whole seconds and include the lookup method/path (recording MBID or ISRC), without credentials or response bodies. Successful verification and publication emits an INFO message; an HTTP 200 alone is not reported as successful publication. Submissions already marked failed by older versions are not automatically requeued.

Enabling verification upgrades the database with a private pre-upgrade SQLite backup, withholds existing unverified references from recognition and statistics, and requeues eligible previously processed submissions once. Existing pending submissions keep their housekeeping deadlines rather than being requeued immediately. References and landmarks are retained; successfully verified references become searchable again, while unresolved submissions follow housekeeping rules. A reference with no usable identifier or submission cannot be automatically verified. Disabling verification restores the offline completeness gate; re-enabling retains successful verification and queues newly unverified references rather than reprocessing the entire collection. Verification is disabled by default.

### Pending metadata housekeeping

For a one-time non-destructive operator pass, run `docker compose exec fingerprints python -c 'from fingerprint_server.settings import Settings; from fingerprint_server.store import Store; Store(Settings().database).request_pending_recheck()'` (use `-f compose.gateway.yaml` for the gateway deployment). The running worker picks up the request within its idle polling interval, snapshots existing pending submissions and checks them regardless of their deadline. MusicBrainz verification must be enabled. This pass never deletes submissions or consumes completed rechecks; successful results publish normally and unresolved results remain pending. Service cooldowns still apply, and start/completion are logged. The request is consumed once, not repeated at every restart; an interrupted pass leaves unprocessed rows pending.

Housekeeping runs in the existing worker, only when both MusicBrainz verification and housekeeping are enabled. Configure these environment settings before starting the server; both Compose deployments pass them through. Recreate the backend after changing them.

| Setting | Default | Meaning |
| --- | --- | --- |
| `FP_HOUSEKEEPING_ENABLED` | `true` | Retry eligible pending submissions and delete exhausted or definitively unresolvable submissions. When false, neither automatic pending rechecks nor automatic deletion runs; ordinary processing continues. |
| `FP_PENDING_MAX_RECHECKS` | `3` | Maximum additional completed unresolved checks after initial processing, from 1 to 1000. Delete the submission after the last unresolved check. |
| `FP_PENDING_RECHECK_DAYS` | `7` | Days between completed checks, at least the seven-day MusicBrainz cache lifetime. Changes apply when scheduling the next deadline; existing persisted deadlines are retained. |
| `FP_BACKGROUND_RECHECK_QUEUE_WINDOW` | `2` | Maximum combined background jobs admitted to the shared queue, including the job being processed (1–1000). Applies to scheduled pending checks and mode/version reverification. |

Automatic background work is admitted gradually at the tail of the same FIFO queue as new uploads. FIFO order uses a separate admission timestamp, not the original upload date. With the default window, at most two background jobs are queued or processing at once; a free slot is replenished when the worker next claims work. New uploads retain their queue position ahead of subsequently admitted background jobs. Reverification of previously processed submissions waits as pending work until admitted, without spending a pending-recheck attempt merely for verification. The setting is an admission window, not parallelism: there is still only one ingestion worker and one shared MusicBrainz cooldown. Lowering the window preserves already admitted jobs and their positions, and pauses further admission until capacity is available. If housekeeping is disabled, admitted scheduled pending checks return to pending without consuming a completed check; required mode/version verification can still run when MusicBrainz is enabled.

For example, set `FP_BACKGROUND_RECHECK_QUEUE_WINDOW=2` in the Compose environment or `.env` file and recreate the backend. Both Compose variants forward this setting. Manual operator passes intentionally keep their existing exclusive, non-destructive behavior and bypass the automatic window; this change does not interrupt or reprioritize a currently running manual pass.

Not-found identifiers, ambiguous ISRC results and incomplete metadata get bounded rechecks. Network failures, service cooldowns and malformed responses do not consume completed rechecks or prove that a submission is unresolvable. Successful verification publishes normally. New submissions with no usable identifier or definitive identifier/coverage conflicts are deleted after processing when housekeeping is enabled; with housekeeping disabled they remain pending. Invalid submission documents retain the explicit failed state.

Schema 5 adds a durable recheck counter, deadline and interrupted-check marker. Existing pending submissions start with zero completed rechecks and a first deadline seven days after migration, regardless of their age or reason; the migration deletes nothing. Restarts and verification-mode activation do not bypass that grace period. Interrupted checks recover without consuming a completed check. An existing no-identifier submission can be deleted when its first scheduled check is due.

When the current verification confirms that neither identifier is available, housekeeping also removes its linked reference and landmarks if the reference is unpublished, has no usable identifier, and no other linked or unlinked submission depends on it. Checking unlinked documents may take time for a large queue. If a dependency cannot be checked, the reference is retained. A concurrent database change during the check defers cleanup to the next scheduled check. Conflicts and exhausted rechecks still delete only the submission; published and shared references are retained. The deletion is atomic, and a later complete submission can recreate a deleted reference. Existing pending submissions are checked only when their existing deadlines are due; migration itself deletes nothing.

After deletion, the submission-status endpoint returns its normal not-found response; uploading the identical document again starts a new submission lifecycle. Scheduled checks are logged as `Housekeeping checking submission`. Every automatic deletion is logged after the database transaction commits with `housekeeping=true`, the submission ID, reason and completed recheck count where applicable. Missing-identifier deletions also report whether the reference was deleted and the number of landmarks removed (`landmarks_deleted`); there is no separate batch total because housekeeping runs continuously in the worker. These are logical SQLite deletions: freed pages can be reused, but the physical database file is not automatically shrunk. No `VACUUM` is performed.
